# Kmt Doc Rules

brain dump の開発文書化、文書の清書、または開発文書の作成・更新に使用する。相談や方針確認だけの依頼では文書を生成しない。

brain dump は意図を保ったまま必要な文書へ一度だけ整理する。

実装計画を文書化しても未承認の実装は開始しない。実装後の再計画、完了処理、Finalization は対象外とする。

## Rules

* ユーザの明示的な指示とリポジトリ固有の文書規約を優先する。
* 未決定事項、例、候補、推測を要求や決定として扱わない。仮定は明示する。
* 既存情報で解決できず、実装結果を左右する不明点だけを Open Questions に残す。
* 実装に直接関係する文書とコードだけを確認し、無関係な履歴や過去の計画を網羅的に調査しない。
* 必要な文書だけを作成または更新し、ソースコードは変更しない。
* 一回の bounded pass 後に追加調査、再計画、整合性確認の反復を開始しない。
* 規則が競合する場合は、依頼範囲を狭く保つ解釈を選ぶ。

## Artifact

リポジトリに正本文書の名称、配置、テンプレート、承認規約がある場合はそれを使用する。規約がない場合は以下を既定とする。

* `docs/current/REQUIREMENTS.md`: 機能要求、非機能要求、制約、受け入れ条件
* `docs/current/SPECIFICATIONS.md`: 外部動作、入出力、状態遷移、エラー、境界条件
* `docs/current/DESIGN.md`: 責務分割、依存方向、外部境界、データ構造
* `docs/current/PRD.md`: 製品背景、対象ユーザ、ゴール、スコープ、成功指標
* `docs/adr/NNNN-short-title.md`: 長期的な変更コストを持つ設計判断
* `docs/plans/active/YYYY-MM-DD-short-name.md`: 複数フェーズ、別セッション継続、承認範囲管理、またはユーザが計画を求めた場合

複数ファイルの変更だけを理由に active plan を作成しない。

承認済み範囲を pending に戻さず、変更された範囲だけを未承認として扱う。ユーザ承認なしに approved と記録しない。

ADR は上書きせず、判断変更時は新しい ADR を作成する。active plan の完了処理や `completed` への移動は行わない。

## Workflow

1. Goal / Scope / Non-goals / Requirements / Open Questions を整理し、必要な既存情報だけを確認する。
2. 確定事項を該当する成果物へ反映し、重複を統合する。仮定と未決定事項は区別する。
3. 更新した成果物だけを確認し、明白な誤記、矛盾、依頼内容との不一致を修正する。
4. 成果物と Open Questions を短く報告する。未承認の実装がある場合は承認対象を示して停止する。

清書だけの場合は実装承認について報告しない。

## Active Plan

新規作成時は `references/active-plan-template.md` を読み、その規則に従う。

既存 plan は既存構造を優先し、テンプレート適合だけを目的とした書き換えは行わない。
