# Plan Before Implementation

## Rule

ユーザの承認を得るまで、本番コード、テスト、設定、依存関係、公開契約、データ形式、永続化形式を変更してはならない。承認前には調査、現状検証、問題再現、開発文書の更新、計画の提示だけを行う。ユーザが今回の作業について明示的に承認待ちを不要とした場合は除く。

## Documents

リポジトリ内の文書を、現在有効な文書、案件ごとの実行計画、長期的な設計判断の3種類に分けて管理する。既存構成がある場合は、その構成と命名規則を優先する。既存構成がない場合は、次を標準とする。

```text
docs/
├── current/
│   ├── REQUIREMENTS.md
│   ├── SPECIFICATIONS.md
│   ├── DESIGN.md
│   └── PRD.md
├── plans/
│   ├── active/
│   │   └── 2026-08-15-short-name.md
│   └── completed/
│       └── 2026-07-10-short-name.md
└── adr/
    ├── 001-short-name.md
    └── README.md
```

`docs/current/` には現在有効なシステム状態だけを記述する。

* `REQUIREMENTS.md`: 機能要求、非機能要求、制約、受け入れ条件
* `SPECIFICATIONS.md`: 外部動作、入出力、状態遷移、エラー時動作、境界条件
* `DESIGN.md`: 責務分割、依存方向、外部境界、データ構造、状態管理
* `PRD.md`: 製品背景、対象ユーザ、課題、ゴール、スコープ、ユーザストーリー、成功指標

現在文書は実装完了後の現在状態と一致させ、変更履歴や一時的な実装手順を記載しない。該当する内容がない文書は作成しない。

複数ファイル、複数フェーズ、設計判断、または別セッションで継続する可能性がある変更では、案件ごとに実行計画を `docs/plans/active/YYYY-MM-DD-short-name.md` へ作成する。計画には必要に応じて次を記載する。

* `Status`, `Objective`, `Current state`, `Scope`, `Out of scope`, `Approach`
* `Affected files`, `Phases`, `Success criteria`, `Validation`, `Risks`, `Progress`, `Decisions`, `Outcome`

各フェーズに目的、前提、対象、対象外、完了条件、検証方法、文書更新、未解決事項、次フェーズへの引き継ぎを記載し、独立して検証可能にする。別セッションで再開できるよう `Progress` に完了フェーズ、次のフェーズ、変更済みファイル、未解決事項、実行済み検証、次に必要な検証を残す。実装と検証が完了したら `Status` と `Outcome` を更新し、計画を `docs/plans/completed/` へ移動する。完了済み実行計画は作業履歴として扱い、現在仕様の正本として使用しない。単一ファイルの明白な小変更など、継続用の作業記録が不要な場合は計画を作成しなくてよい。

長期的な変更コストを持つ重要な設計判断では、1判断につき 1つの ADR を `docs/adr/NNNN-short-title.md` に作成する。ADR には `Status`, `Date`, `Context`, `Decision`, `Alternatives considered`（採用しなかった案とその理由）, `Consequences`, `Related plans`, `Supersedes`, `Superseded by` を記載し、`docs/adr/README.md` の索引を維持する。既存 ADR の判断を上書きせず、判断を変更する場合は新しい ADR を作成して以前の ADR を `Superseded` に変更する。すべての変更に ADR を作成せず、長期的な判断に限る。

内容が変わる文書だけを作成または更新し、同じ説明を複数の文書へ複製しない。必要なら正本を1つ決め、他の文書から参照する。空文書、将来利用するかもしれないだけの文書、実装内容をそのまま説明しただけの文書は作成しない。文書と実装が矛盾する場合は矛盾を明示し、推測でどちらかを正しいものとして扱わない。

完了時には、実行計画の成功条件、必要な検証、現在有効な要求・仕様・設計、必要な ADR、計画の `Outcome` と再開不要な最終状態を確認する。

## Approval handoff

ユーザへ、現状、要求の解釈、前提、変更対象、対象外、設計方針、フェーズ、成功条件、テスト、検証方法、リスク、更新文書を提示し、承認が必要であることを明示する。

「実装してください」「進めてください」「承認します」など、提示した計画への肯定を承認と扱ってよい。質問、追加要件、懸念だけを承認と解釈しない。承認されたフェーズを越えて実装しない。

完了時点では、実装を開始せず、現状、要求、設計、成功条件、検証方法、承認対象が明確になっていなければならない。
