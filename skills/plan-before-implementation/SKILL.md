# Plan Before Implementation

## Rule

ユーザーの承認を得るまで、本番コード、テスト、設定、依存関係、公開契約、データ形式、
永続化形式を変更してはならない。承認前には調査、現状検証、問題再現、開発文書の更新、
計画の提示だけを行う。ユーザーが今回の作業について明示的に承認待ちを不要とした場合は除く。

## Inspect

計画前に次を確認する。

* グローバルおよびリポジトリ固有の指示
* README、CONTRIBUTING、開発文書、ADR
* ビルド、テスト、CI、lint、format の設定
* 作業ツリーの既存変更
* 要求された動作の入口、所有するコード、呼び出し関係、データフロー
* 状態の所有者、外部 I/O、副作用、エラー処理
* 関連テスト、類似実装、公開 API、データ形式、永続化形式

ファイル名や推測だけで判断せず、実際のコードと設定を確認する。既存変更を今回の変更と
誤認しないこと。

## Define the outcome

要求を実装手段ではなく、観測可能な結果として整理する。

* 達成する結果と現在の問題
* 期待される外部動作と維持する既存動作
* 対象範囲と対象外
* 明示された制約と、リポジトリから確認できる制約
* 未確定事項と採用する仮定

未確認の推測は確定事項として扱わない。選択によって動作、互換性、安全性、範囲が大きく
変わる場合だけユーザーへ確認する。

## Design the change

変更する判断、状態遷移、入力検証、変換、I/O、永続化、通信、UI、OS、ハードウェア、
エラー復旧の責務と配置を確認する。

* 判断や状態遷移を外部 I/O へ埋め込まない。
* 外部固有型を内部ロジックへ必要以上に流入させない。
* 異なる理由で変わる責務を混在させない。
* 同じ判断を複数箇所へ追加しない。

新しい抽象化を提案する場合は、隔離する具体的な変化または外部境界、可能になるテスト、
既存構造より有利な理由を示す。将来の推測や形式的な層構造だけを理由に追加しない。

## Plan tests and validation

変更する動作ごとに、回帰を検出する最小のテストとリポジトリ所定の検証を定義する。

* バグ修正では、可能な限り修正前に失敗する再現テスト
* 正常系、境界値、無効入力、エラー経路、状態遷移のうち影響するもの
* format、コンパイル、静的解析、unit/integration test、target build
* 必要な実機または手動検証
* 実行できない検証、その理由、代替検証

テストがない場合も、ホストテスト、純粋な判断ロジックのテスト、外部境界を置き換えた
統合テストを検討してから、手動検証だけでよいか判断する。

## Documents

既存構成に従い、内容が変わる文書だけを作成または更新する。

* `PLAN.md`: 目的、現状、範囲、対象外、前提、方針、変更対象、フェーズ、成功条件、
  検証方法、リスク、未確定事項
* `REQUIREMENTS.md`: 要求、制約、受け入れ条件を変更する場合
* `SPECIFICATIONS.md`: 外部動作、入出力、状態遷移、エラー時動作を変更する場合
* `DESIGN.md`: 責務、依存方向、外部境界、状態管理を変更する場合
* ADR: 長期的な変更コストを持つ重要な判断を行う場合

空文書、同じ説明の反復、すべての変更に対する ADR は作らない。

複数フェーズは独立して検証可能にする。各フェーズへ目的、前提、対象、対象外、完了条件、
検証方法、文書更新、未解決事項、次フェーズへの引き継ぎを記載する。

## Approval handoff

ユーザーへ、現状、要求の解釈、前提、変更対象、対象外、設計方針、フェーズ、成功条件、
テスト、検証方法、リスク、更新文書を提示し、承認が必要であることを明示する。

「実装してください」「進めてください」「承認します」など、提示した計画への肯定を承認と
扱ってよい。質問、追加要件、懸念だけを承認と解釈しない。承認されたフェーズを越えて
実装しない。

完了時点では、実装を開始せず、現状、要求、設計、成功条件、検証方法、承認対象が
明確になっていなければならない。
