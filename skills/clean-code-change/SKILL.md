# Clean Code Change

## Preconditions and scope

実装前に、ユーザの承認、対象フェーズ、成功条件、検証方法、必要な開発文書、作業ツリーの既存変更を確認する。承認済み計画がなければ実装せず、`plan-before-implementation` を使用する。

承認された動作、モジュール、設計、依存関係、文書だけを変更する。要求外のリファクタリング、一括リネーム、全面的なフォーマット、設定可能性、フォールバック、互換レイヤー、将来用の拡張点、ログ、メトリクス、不具合修正を混ぜない。範囲外の問題は修正せず報告する。

## Re-plan conditions

次の場合は実装を止め、文書を更新して再承認を得る。

* 承認済み設計では要求または成功条件を満たせない。
* 新しい依存関係、公開 API、データ形式、永続化形式、別のアーキテクチャが必要になる。
* 対象範囲が大きく広がる。
* セキュリティ、安全性、データ損失、互換性への新しい影響が判明する。
* 既存実装が計画の重大な前提と異なる。

## Implement

### Regression evidence

バグ修正では、可能な限り先に再現テストを追加して修正前の失敗を確認する。新機能では、要求された観測可能な動作または受け入れ条件を先にテストへ表す。自動テストが適さない場合は、理由と代替検証を記録する。

### Responsibilities

* 判断、状態遷移、入力検証を I/O、UI、永続化、通信、OS、ハードウェアから分離する。
* ドライバ、アダプター、ハンドラー、組み立てコードへアプリケーション判断を置かない。
* 同じ判断を複数箇所へ複製せず、状態の所有者と更新箇所を明確にする。
* 外部固有型を内部境界へ必要以上に持ち込まない。

新しい抽象化は承認済みのものに限る。実装中に必要性が判明した場合は再計画する。単一実装の形式的なラッパー、委譲だけの層、投機的な汎用化を追加しない。

### Readability

* 名前は役割、意図、ドメイン上の意味を表し、必要な単位を明示する。
* 関数へ異なる理由で変わる判断、変換、I/O を混在させない。
* 制御フローと状態遷移を追跡可能にし、未知の状態を既定分岐で隠さない。
* コメントは理由、外部制約、非自明なトレードオフを説明し、コードを言い換えない。

### State, side effects, and errors

* 新しい可変グローバル状態を追加せず、状態の寿命、所有者、更新箇所を明確にする。
* 判断と副作用を可能な範囲で分離し、任意の sleep を同期手段にしない。
* タイムアウト、リトライ、フォールバック、キャッシュを暗黙に追加しない。
* 並行処理では所有者、同期、終了、キャンセル、エラー伝播を明確にする。
* エラーを握り潰さず、ログだけで成功扱いしたり根拠のない既定値へ置換したりしない。
* 元の原因を保って文脈を加え、復旧できる層だけで処理する。
* 部分失敗、タイムアウト、キャンセル、無効入力を契約どおり区別する。

### Tests

テストは実装手段ではなく、変更した観測可能な動作、公開契約、状態遷移、境界条件、無効入力、エラー経路、回帰条件を検証する。

実装を通すために既存テストを削除、skip、弱体化しない。根拠なく期待値を変えず、本番アルゴリズムの複製、テスト対象の判断自体の mock、sleep 同期、実行順序依存を避ける。

## Validate and finish

変更単位では最も狭い関連テストを実行し、その後リポジトリ所定の順序で format、コンパイル、静的解析、テスト、target build、必要な実機または手動検証を行う。

差分から要求外の変更、生成物、デバッグコード、一時ログ、未使用コード、意図しない API や依存関係の変更を除き、実装によって意味が変わった文書だけを同期する。既存の失敗と今回の失敗を区別し、必要な検証が失敗または未実行なら完了としない。

完了報告には、実装したフェーズ、変更した動作とファイル、テスト、文書、検証コマンドと結果、未実行の検証、計画との差異、範囲外で見つけた問題、残るリスクを含める。
