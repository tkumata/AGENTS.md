# Clean Code Review

## Rule

実装を正当化するのではなく、具体的な欠陥、回帰リスク、承認済み設計からの逸脱を探す。
レビュー中は原則として変更せず、まず指摘を作成する。修正はユーザーが依頼した場合だけ
別工程で行う。件数を満たすための推測や好みの指摘を作らない。

## Inputs

ユーザー要求、承認済み `PLAN.md`、関連する要求・仕様・設計・ADR、リポジトリ固有指示、
Git 差分、変更箇所の周辺コード、呼び出し元と呼び出し先、関連テスト、検証結果、CI 設定を
必要な範囲で確認する。差分だけで動作を判断しない。

## Severity

* **Critical**: データ損失、認証・認可の欠落、重大な安全性問題、広範囲な停止、
  回復不能な永続化破損
* **High**: 主要機能の不動作、重大な回帰、競合やデッドロック、危険なエラー状態、
  公開契約の非互換、状態遷移の破綻、継続的な資源リーク
* **Medium**: 特定条件の誤動作、エラーの握り潰し、不正確な timeout/retry、
  具体的な変更リスクを生む責務混在、不要な依存、現実的な回帰を逃すテスト、
  文書との意味ある不一致
* **Low**: 誤解を招く命名やコメント、重複した判断、不要な複雑性や抽象化

影響に基づいて評価し、単なる好み、整形、別の書き方、行数、カバレッジ率だけを理由にしない。

## Review

### Scope and requirements

* 差分が承認された要求、設計、フェーズ、成功条件に対応しているか。
* 未実装の要求、文書にない動作、暗黙の既定値変更、部分失敗の成功扱いがないか。
* 要求外のリファクタリング、形式変更、依存関係、設定、フォールバック、生成物がないか。
* 正常時、境界条件、無効入力、エラー時に既存契約を維持するか。

各問題は、発生条件、実際の制御フロー、違反する要求または契約で説明する。

### Responsibilities and dependencies

* 判断、状態遷移、入力検証が適切な責務にあり、I/O、UI、永続化、通信へ分散していないか。
* 同じ判断が複数層にないか。外部型が内部境界を越えたり、依存方向を逆転させたりしていないか。
* 新しい interface、trait、wrapper、factory、utility が具体的な変化、外部境界、
  テスト上の必要性を隔離し、呼び出し側を実際に単純化しているか。
* 共通化したコードが同じ概念と変更理由を持つか。投機的な汎用化や一行委譲だけでないか。

形式ではなく、誤動作または具体的な変更シナリオへの影響を指摘する。

### Readability, state, and resources

* 名前が役割、意図、単位、副作用を正しく表すか。
* 関数の判断、変換、I/O、ログが追跡でき、状態と分岐が不必要に複雑でないか。
* コメントが理由や制約を説明し、コードと矛盾していないか。
* 可変状態の所有者、寿命、更新箇所、状態遷移、時刻依存が明確か。
* 並行処理の同期、lock 範囲、終了、キャンセル、エラー伝播に競合や停止リスクがないか。
* メモリ、file、socket、lock、task、timer、callback、hardware handle、buffer の所有と解放、
  境界、容量に問題がないか。

### Errors

* エラーを無視、ログだけで成功、既定値や正常値と同じ sentinel に置換していないか。
* 元の原因を失わず、復旧可能な層で処理し、不可能なら上位へ伝播しているか。
* 部分失敗、timeout、cancel、無効入力、一時的失敗を契約どおり区別しているか。
* エラー時に状態、cleanup、rollback が中途半端にならないか。
* 無制限 retry、retry storm、偽の fallback、誤った成功表示がないか。

### Tests

変更した観測可能な動作、状態遷移、境界値、無効入力、エラー経路、回帰条件をテストが
検証するか確認する。

修正前にも通る再現テスト、実装アルゴリズムの複製、テスト対象自体の mock、弱い assertion、
sleep 同期、実行順序や共有状態への依存、時刻や乱数による flakiness、既存テストの削除や
skip がないか確認する。

### Documents and validation

* 実装が `PLAN.md`、要求、仕様、設計、ADR と意味上整合し、未実装機能を完了扱いしていないか。
* 必須コマンドが対象プラットフォームで成功し、変更した動作を実際に検証しているか。
* 未実行の検証、既存の失敗、新しい警告や失敗が正確に区別されているか。

## Finding format

指摘を severity 順に、次の形式で記載する。

```text
[Severity] 簡潔な問題名

Location:
- path/to/file:line

Problem:
- 何が問題か

Impact:
- どの条件で何が起き、どの要求または契約に違反するか

Evidence:
- 問題を示すコードまたは制御フロー

Recommended direction:
- 必要最小限の修正方向
```

行番号が不明なら関数、型、差分箇所を示す。根拠のない将来懸念、個人的な書き方、
formatter が扱う問題、今回の差分が悪化させていない既存問題は主要指摘にしない。

## Output

最初に指摘を severity 順で列挙し、その後に前提、未確認事項、未実行の検証、残るリスク、
総合評価を必要な範囲で記載する。

指摘がなければ、重大な問題は確認できなかったこと、確認範囲、未確認の検証、残るリスクを
明示する。「問題を発見しなかった」と「正しさを証明した」を混同しない。
