# 文書仕様作成

## 前提

- 前提として AGENTS.md と GEMINI.md と CLAUDE.md とプロジェクト文書を優先し、矛盾時はソースコードを正とする。
- 不明点は推測で埋めすぎず、文書の穴として明示する。

## 対応対象

- `要件定義書`: 背景、目的、スコープ、機能要件、非機能要件、制約、受け入れ条件。
- `設計書`: 構成、責務分割、データモデル、外部連携、エラー処理、運用観点。
- `仕様書`: 入出力、境界値、状態遷移、例外系、互換性、外部契約。
- `TODO 文書`: 実装タスク、検証タスク、未解決事項、優先度。

## 実行手順

1. 既存資料を収集し、対象文書と更新範囲を確定する。
2. 既存コードと既存文書の差分を確認し、現行挙動を基準に事実を整理する。
3. 未確定事項を「確定」「仮定」「未定」に分類する。
4. 文書の章立てを決め、各章に必要な入力情報を埋める。
5. 数値条件、境界値、エラー時挙動、制約条件を明文化する。
6. 受け入れ条件をテスト可能な文に落とし込む。
7. 用語揺れ、矛盾、抜け漏れを検査し、改訂履歴を更新する。

## 記述ルール

- 1 文 1 意味を基本とし、主語を省略しすぎない。
- 必須要件と推奨要件の強制度は文脈で明確に分離する。
- 可能な限り定量化する。例: 「速い」ではなく「95 パーセンタイル 300ms 以下」。
- エラー条件は発生条件、返却内容、利用者への影響、回復方法を分けて書く。
- 仕様変更時は、互換性影響と移行方針を必ず追記する。

## 最小チェックリスト

- 目的とスコープが 3 行以内で説明できる。
- 機能要件に入力、処理、出力、失敗時がそろっている。
- 非機能要件に性能、可用性、セキュリティ、運用要件がある。
- 受け入れ条件が観測可能な形になっている。
- 未確定事項が文書内で識別可能になっている。
